fix(generator): keep named-number fields inside their declared value set

A type declared with a named-number list admits ONLY the listed numbers:

    Epf1RoleType ::= INTEGER { native(0), barred(1), ... cmfbMember(7) }
    SDP-Type     ::= ENUMERATED { sDP-offer(0), sDP-answer(1) }

The resolver already compacts those bodies into the field's type expression
("INTEGER{native(0),barred(1),...}"), but the generator never looked: every
INTEGER and ENUMERATED was filled with nextInt(100_000). A generated MMTel
record carried epf1-Role-of-Node = 85038 for a type that allows 0..7, and 27
of the 37 named-number fields in that one record were out of range. Across
2000 records of an EMM-accepted reference capture, all 26912 such fields hold
a declared value - not one exception. 2545 types across 130 of the 808 schema
modules declare a named-number list.

The random fallback now picks from the declared numbers when the type lists
any, and falls back to the old free range for a plain unconstrained INTEGER.

yml rule examples are held to the same bar. Rules match on a name SUBSTRING,
so a rule seeded with 15/127/842 for "duration" would otherwise happily fill a
field that only admits {0,1}; its examples are now usable only when every one
of them is a value the type declares.

Value sources ahead of the random fallback are untouched, so a field the AI
layer already answers correctly (recordType = 83) keeps its value.
